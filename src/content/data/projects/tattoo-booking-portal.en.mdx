## What it is

Booking requests come in through the <ProjectLink slug="tattoo-sites">websites of a tattoo studio and its artists</ProjectLink>. They used to be loose e-mails. The portal is the one place where every request ends up and where the artists handle it.

The artists use it mostly on phones and iPads, so the interface is built for those first. Its interface is in German.

## The path of a request

<Steps>
  <Step title="Form">
    The website checks the request and hands it to the portal. It never writes to the database
    itself.
  </Step>
  <Step title="Intake">
    A request counts as received only once it is stored. A retry reuses the same submission ID, so a
    flaky connection never creates a duplicate.
  </Step>
  <Step title="Assignment">
    A request through an artist's own website belongs to that artist at once. A request through the
    studio website that names an artist goes to that artist. Without a preference it lands in the
    shared inbox, where exactly one artist takes it.
  </Step>
  <Step title="Handling">
    New, in discussion, appointment arranged, completed. For every request the portal shows the next
    step.
  </Step>
  <Step title="Hand-over">
    An artist can hand a request over to another one. When the person chose a specific artist, that
    needs their consent first, and the proof is filed with the request.
  </Step>
  <Step title="Deletion">Six months after a request is closed, the portal deletes it.</Step>
</Steps>

Artists get at most one summary e-mail per day: how many unseen requests are waiting, with no customer data in it.

## Who sees what

Who sees a request depends on which website it came through and whose it is.

| Who                      | Through an artist's own website | Studio website, in the shared inbox | Studio website, with an artist |
| ------------------------ | ------------------------------- | ----------------------------------- | ------------------------------ |
| Responsible artist       | everything                      | nobody yet                          | everything                     |
| Other artists            | nothing                         | everything, may take it             | nothing                        |
| Studio coordination      | nothing                         | everything, may assign it           | key data only                  |
| Technical administration | nothing                         | nothing                             | nothing                        |

The studio coordination distributes requests but does not handle other artists' requests. Of another artist's request it sees key data only: date, status, artist and how the artist got it. The technical administration is me. I run the portal and manage the accounts without seeing the content of real requests.

The database enforces these boundaries, with row-level security on the tables, and not just the interface.

## How I built it

<Callout title="Decided: a database instead of folders">
  At first every request went into a Nextcloud as a PDF. That stopped working once requests needed a
  status, an unambiguous take-over, hand-overs and duplicate protection. On folders and files I
  would have had to rebuild all of that. In a database it is columns, constraints and access rules.
</Callout>

- **Rules as database tests.** SQL tests check who may see and do what directly against the database, including concurrent access.
- **Demo data for every case.** One command rebuilds the database with close to 50 requests that together cover every case of the inbox. The images on this page show that demo data.
- **Test requests in production.** A revocable test key lets me check the whole path through the real forms. Test requests are marked permanently and deleted after 14 days.
- **Backup.** Once a week the portal backs up database and files to a private store in Frankfurt. It keeps the two newest complete backups, so a broken one never replaces the only good one.
- **Data in the EU.** Portal and database run in Frankfurt.

The portal lives in the same repo as the websites, so the form schema and the intake can change together. It still is its own app with its own database and credentials.
